# PLAN — learning-paths-content

_Work item slug: learning-paths-content. Plan produced by factory-planner. Source: factory/work/learning-paths-content/REQUEST.md._

## Summary

This work item builds the learning-path and content system — the second foundational feature, sitting on top of the accounts/auth foundation, that progress tracking (FR-PROG), ratings (FR-RATE), search (FR-SEARCH-001/002/003), and certificates (FR-CERT) all depend on. It adds the content half of the product data model (paths, courses, content items, tagging taxonomy, version history, glossary terms), a file-based content pack in the repo plus an idempotent importer that loads it into Postgres (the FR-ADMIN-001 "manual process" for R1, with no admin UI), a Markdown rendering pipeline for original platform-hosted lessons including contextual glossary links, curated-link cards that open externally with source attribution, and the public browse surface: a paths index, per-role landing pages (FR-SEARCH-004), per-role-per-level path pages, course pages, lesson pages, and a glossary. It seeds a representative content pack across both R1 role archetypes and all three levels — enough real content to make every mechanism demonstrable and testable end to end, deliberately **not** the full final content library, which is content-sourcing work running in parallel outside engineering per the roadmap. No progress, rating, bookmark, search-index, or certificate table is created; those items own their own migrations and will hang off the stable `ContentItem`/`Course`/`Path` ids created here.

## Requirement IDs satisfied

Primary:

- **FR-PATH-001** — a path is a stored, ordered sequence of content items for a given role x level combination (`Path` -> ordered `Course`s -> ordered `ContentItem`s).
- **FR-PATH-004** — every content item is tagged with role(s), level, topic(s), format, estimated duration, and source type; validated at import and displayed in the UI.
- **FR-PATH-005** — original, platform-hosted lessons: Markdown body rendered by the platform, with optional short video (CDN-hosted `<video>` plus captions track).
- **FR-PATH-006** — curated items link out to external resources, opening in a new tab, with visible source attribution.
- **FR-PATH-007** — every content item stores `lastReviewedAt`, a review cadence, a monotonic `version`, and an append-only `ContentItemVersion` snapshot history.
- **FR-PATH-008** — lesson bodies contain contextual glossary links (`[term](glossary:slug)`) that render as accessible inline definitions linking to a glossary term page; the importer fails on an unresolved glossary reference.
- **FR-PATH-009** — a signed-in user can switch role and/or level at any time from a path page and land on the corresponding path; the retention-of-progress half is guaranteed structurally (see Decisions #6) and becomes observable when FR-PROG lands.
- **FR-ADMIN-001** — content is managed as a git-versioned structured file pack plus an idempotent `npm run content:import` importer; no admin UI.
- **FR-SEARCH-004** — each role archetype has a public landing page describing the path and its three levels.
- **NFR-MAINT-001** — the tagging taxonomy (roles, levels, topics, formats, source types) is formally documented (`docs/content/taxonomy.md`) and versioned (`content/taxonomy.yaml`, in git).
- **NFR-MAINT-002 / -003** — curated items default to a 90-day review cadence, original items to 365 days; both are stored per item and surfaced as a "last reviewed" date in the UI, and the review workflow is documented.
- **NFR-COMP-001** — curated content is linked, never rehosted or scraped; publisher attribution is displayed on every curated item.

Partial / seeded (full satisfaction needs later work items or content sourcing; recorded for traceability):

- **FR-PATH-002** — the system supports and ships **populated** Technical Builder and Executive/Non-Technical paths at all three levels, but with a representative seed pack (see Scope: seed content volume), not the full launch library. Structurally complete; editorially a beta seed. This is the one requirement this item knowingly only partly discharges, per REQUEST.md and roadmap section 6.
- **FR-ACC-008** — the "browse public content and path descriptions without an account" half becomes real here: every path/course/lesson/glossary route is anonymously readable. The auth item already built the other half.
- **NFR-A11Y-002 / -004** — new pages are built responsive, keyboard-operable, with the existing focus-visible convention; the glossary tooltip is CSS/focus-driven with no JS dependency. The full WCAG 2.1 AA audit (NFR-A11Y-001) remains a separate item.
- **NFR-A11Y-003** — the seeded zero-knowledge lessons are written to plain-language rules and the authoring guide states them; the standalone style guide the requirements call for (section 5 open item) is not authored here.
- **NFR-SEC-007** — lesson bodies are author-controlled, not user-submitted, but are still rendered without `dangerouslySetInnerHTML` and with raw HTML in Markdown left inert (see Decisions #3), so the rendering pipeline cannot become a stored-XSS vector when user-submitted text arrives with FR-RATE.
- **NFR-SCALE-002** — indexes on the content tables sized for the year-one 5,000-content-item target; search-specific indexing is deferred to the FR-SEARCH work item that will choose the search technology.
- **NFR-SCALE-003** — original lesson video is referenced by absolute CDN (Vercel Blob) URL and never proxied through the app origin, per the shipped infrastructure decision.
- **NFR-MAINT-004** — Playwright coverage for browsing a path, viewing a lesson, following a curated link's attribution, the glossary, and switching paths. The course-**completion** journey depends on FR-PROG and is explicitly not attempted here; nothing in this item blocks it.
- **NFR-MAINT-005** — content-import procedure documentation, which the requirement names explicitly.

## Scope

### In scope

- Prisma content schema: `RoleProfile`, `Path`, `Course`, `PathCourse`, `CourseItem`, `ContentItem`, `ContentItemVersion`, `Topic`, `GlossaryTerm`, plus `ContentFormat`, `SourceType`, `ContentStatus` enums, and one additive migration.
- The `content/` file pack format (Markdown + YAML frontmatter for prose; YAML for structure and taxonomy) with a documented authoring guide.
- A loader + validator (Zod) that reads and cross-checks the pack, and an idempotent importer (`npm run content:import`, plus `--dry-run`) that upserts into Postgres, bumps versions on real change, snapshots history, and retires removed items rather than deleting them.
- Markdown rendering for original lessons (server-side, component-mapped, no `dangerouslySetInnerHTML`), including glossary links, external links, code blocks, and an optional video block with captions.
- Public routes: `/paths`, `/paths/[role]`, `/paths/[role]/[level]`, `/courses/[slug]`, `/lessons/[slug]`, `/glossary`, `/glossary/[slug]`.
- A path switcher that changes the signed-in user's role/level (reusing the existing `PATCH /api/account/profile`) and navigates to the new path; anonymous visitors get plain navigation.
- Dashboard, site header, and home page updated to route into the new content surface.
- A seed content pack: 2 role profiles, 6 paths (2 roles x 3 levels), 12 courses, ~20 unique content items (at least 6 original lessons with real plain-language text, at least 10 curated links to genuinely stable sources), at least 2 items deliberately shared across two paths to exercise overlap, and at least 15 glossary terms.
- Unit/component tests (Vitest + RTL) and Playwright e2e for browsing, lessons, curated attribution, glossary, and path switching; a Playwright global setup that imports the pack so the suite is self-sufficient.
- Docs: content architecture decision record, authoring guide, taxonomy doc, README section, provisioning-checklist additions.

### Out of scope (explicitly)

- **FR-PATH-003** (Engineering Leader and Investor paths) — R2. The schema, importer, and routes are role-agnostic and already handle all four `RoleArchetype` values; only the content files and `RoleProfile` entries for those two roles are absent. Adding them later is a content-pack change with no code change.
- **FR-PATH-010** (user-assembled custom paths) — P2. See Decisions #5 for why `@@unique([roleArchetype, level])` does not block it.
- **FR-PROG-001/002/003** — no `Progress` model, no completion controls, no resume, no percent-complete. Decisions #6 records the schema commitment that makes it a purely additive migration.
- **FR-RATE-\*** — no `Rating` model, no stars, no free-text feedback, no aggregate display.
- **FR-SEARCH-001/002/003** — no full-text search, no filter UI, no bookmarks. Tag data exists and is displayed, but nothing queries by it. The search-technology decision (requirements section 5) stays open for that item, including whether the tag columns need GIN indexes or a tsvector column.
- **FR-CERT-\*** — R2.
- **FR-ADMIN-002 through -007** — no admin UI, no moderation queue, no automated staleness flagging, no analytics view. `nextReviewDueAt` is stored (Decisions #7) but nothing reads it yet.
- **NFR-AVAIL-004** (automated curated-link availability checking) — R2. Link rot in the seed pack is a manual check.
- **Video production or upload.** The renderer and schema support video; no media asset is created or uploaded by this item, and the seed pack therefore ships no video URL at all, live or placeholder (see the manual checklist and Risks #3).
- **Re-deciding stack, hosting, DB, auth library, or styling** — fixed by the two shipped items.

### Note on size

This is a large item, comparable to user-accounts-auth, but it is one coherent unit: the schema, the pack format, the importer, and the rendering are useless in isolation — a schema with no importer has no content, an importer with no routes has nothing to prove it worked. If the builder finds it too large in flight, the clean split points are: **(A)** tasks 1-14 (deps, schema, migration, loader/validator, importer, content pack), **(B)** tasks 15-32 (rendering components and routes), **(C)** tasks 33-50 (tests and docs). Prefer finishing (A) then (B) on one branch over splitting the plan into separate work items.

## Decisions made by this work item

Bias carried from the two shipped items: solo maintainer, free educational site, low-ops, no new external services unless a requirement forces one.

1. **Content authoring/import format = a git-versioned file pack in `content/` (Markdown + YAML frontmatter for prose, YAML for structure), loaded into Postgres by an idempotent importer script; Postgres is the runtime source of truth, the files are the authoring source of truth.** This is the FR-ADMIN-001 "structured file import" reading. Rationale: (i) later R1 features force the content into the database anyway — FR-PROG needs per-item progress rows, FR-RATE needs per-course ratings, FR-SEARCH needs queryable tags, and FR-ADMIN-002's R2 admin UI needs writable rows — so a purely file-based, build-time-only content system would have to be rebuilt within two work items; (ii) authoring in files gives free diff, review, and history for a solo maintainer, and needs zero new infrastructure or accounts; (iii) the importer is the same mechanism used to seed CI and local dev, so the content-ops process and the test-fixture problem are solved by one thing. Rejected: **(b) spreadsheet/CSV import** — the requirement names it as an option and it is fine for tabular metadata, but multi-paragraph lesson bodies in spreadsheet cells are miserable to author and review, it has no meaningful diff, and it invites encoding and quoting bugs; a CSV-to-pack converter can be added later if a non-engineer curator needs one, without changing the schema. Rejected: **(c) MDX/Markdown files rendered directly at build time with no database rows** — lowest ops today, but has no stable content id for `Progress`/`Rating` foreign keys, cannot be edited by the R2 admin UI, and makes FR-SEARCH a build-time index problem; it optimizes this one work item at the cost of the next four. Rejected: **(d) a hosted headless CMS (Sanity/Contentful/Payload)** — real editorial tooling, but a new external account, a new cost curve, a second system holding product data, and a synchronization problem for a platform whose only content editor is the person who owns the repo.
2. **The importer never deletes; it upserts and retires.** A content item removed from the pack is set to `status = RETIRED` (with `retiredAt`), not deleted, because future `Progress`, `Rating`, and `Certificate` rows will reference it and a learner's completed history must not vanish because a curator dropped a link. Retired items are excluded from path rendering. Re-adding the same slug un-retires it. The importer's write path runs in a single Prisma transaction and prints a created/updated/unchanged/retired summary; `--dry-run` validates and prints the same summary without writing. Rejected: delete-and-recreate on every import — simplest to write, but every import would rotate every id, which is exactly the corner this item was told not to paint the schema into.
3. **Original lesson rendering = `react-markdown` + `remark-gfm` in a server component, with a custom component map and raw HTML left inert.** Bodies are stored as Markdown text in the database and parsed to a React element tree at render time — no HTML string is ever produced, so there is no `dangerouslySetInnerHTML` anywhere in the pipeline and no sanitizer to get wrong. The component map is where FR-PATH-008 and FR-PATH-006 are implemented: an `href` beginning `glossary:` renders `<GlossaryLink>`, any other absolute URL renders an external anchor with `target="_blank" rel="noopener noreferrer"` and a visible host, and code blocks and headings get styled, id-anchored variants. Rejected: **(b) MDX** (`next-mdx-remote` or runtime `@mdx-js/mdx`) — component-in-content power we do not need for text-and-video lessons, and runtime MDX compilation of database-stored content is expensive and effectively executes authored code, which is a bad property to hand to a future admin UI. Rejected: **(c) `marked`/`markdown-it` producing an HTML string plus `dangerouslySetInnerHTML` (with `rehype-sanitize`/DOMPurify)** — fastest render, but reintroduces exactly the injection surface the codebase has so far avoided, for no benefit.
4. **Video (FR-PATH-005) = an optional frontmatter `video` block (`url`, `captionsUrl`, `posterUrl`, `durationSeconds`) rendered as a native `<video controls preload="metadata">` with a `<track kind="captions">`, pointing at an absolute Vercel Blob CDN URL.** This honours the shipped NFR-SCALE-003 decision (media served from the CDN, never proxied through a serverless function), needs no player library, no transcoding pipeline, and no new dependency, and captions are mandatory in the schema when a video is present (accessibility). Rejected: embedding YouTube/Vimeo iframes — free hosting and adaptive bitrate, but it is third-party-hosted rather than "platform-hosted" as FR-PATH-005 words it, it drags third-party cookies into a site that still owes a cookie-consent mechanism (NFR-COMP-003), and it would need the `frame-ancestors` CSP posture revisited. Rejected: a JS player (Video.js, Mux Player) — a dependency and a client bundle for functionality the native element already provides for short lessons. **Seed-pack consequence (confirmed with the human, Risks #3):** the R1 pack ships no video URL, live or placeholder — the designated video lesson's `video` block is committed commented out until a real asset is uploaded via the manual checklist, because a placeholder CDN URL would render a visibly broken player on a public page. The rendering path is therefore proven by a `lesson-video` component test plus the captions-required schema test, not by e2e against seeded data.
5. **Content hierarchy = `Path` -> `Course` -> `ContentItem`, with many-to-many ordered joins at both levels.** The requirements use all three nouns as distinct addressable things: FR-PATH-001 orders *content items* within a path, FR-PROG-001 tracks completion per *content item*, FR-PROG-003 shows percent complete per *path and course*, FR-RATE-001/003 rate a *course* and a *path*, and FR-CERT-001/002 issue certificates for a *course* and a *path*. Modelling only two levels now would force a restructuring migration when FR-RATE or FR-CERT lands. Both joins are many-to-many (`PathCourse`, `CourseItem`, each carrying `position`) rather than a parent foreign key, because FR-PATH-009's "retaining progress on previously completed items where content overlaps" is only meaningful if the same item, and the same course, can appear in more than one path — a `ContentItem.courseId` column would make overlap structurally impossible. `Path` carries `@@unique([roleArchetype, level])`: at R1/R2 there is exactly one curated path per role x level. FR-PATH-010's custom paths are user-owned assemblies and will be a separate `UserPath` model, not extra rows here, so this constraint does not block them.
6. **Progress and rating attachment points are fixed now, in writing, and nothing else is built for them.** Later items must key progress on `(userId, contentItemId)` and ratings on `courseId`/`pathId`, all referencing the `String @id @default(cuid())` primary keys created here (stable across imports per Decisions #2). That single commitment is what makes FR-PATH-009's retention half true by construction — an item shared by two paths is one row, so completing it in one path is already completing it in the other — and it means FR-PROG is a purely additive migration. No `Progress`, `Rating`, `Bookmark`, or `Certificate` table, and no columns "for later", are added here.
7. **Review cadence is stored per item, derived at import.** `sourceType = CURATED` defaults to `reviewCadenceDays = 90` (NFR-MAINT-002's 8-12-week staleness finding), `ORIGINAL` to `365` (NFR-MAINT-003); either can be overridden per item in frontmatter. The importer maintains `nextReviewDueAt = lastReviewedAt + reviewCadenceDays`, indexed. Nothing reads that column at R1 — it exists because it is free to write now and because FR-ADMIN-004/-007 (R2/P2 staleness flagging) would otherwise need a backfill over the whole library. The `lastReviewedAt` date is displayed on lesson pages and item cards so the freshness promise is visible to learners, not just to curators.
8. **Version history lives in the database as well as in git.** FR-PATH-007 requires the *system* to store version history, and "git log" is not a system feature a future admin UI can write to. Each `ContentItem` carries a monotonic `version` and a `contentHash` of its normalized payload; when the hash changes, the importer increments `version` and appends a `ContentItemVersion` row holding a full JSON snapshot plus an optional author-supplied `changeNote`. Unchanged items are left completely untouched, so re-running the importer is a no-op. Rejected: relying on git history alone (invisible to the app, unusable by the R2 admin UI); rejected: column-level audit triggers in Postgres (opaque, unportable, and outside Prisma's model).
9. **Topics are data; roles, levels, formats, and source types are enums.** FR-ADMIN-003 (R2) expects the taxonomy to be manageable, and topics are the only open-ended axis — new AI subject areas appear constantly. So `Topic` is a table (slug + label, implicit many-to-many to `ContentItem`) declared in `content/taxonomy.yaml`, while `RoleArchetype` and `ProficiencyLevel` reuse the **existing** Prisma enums from the auth item (no duplication) and `ContentFormat`/`SourceType`/`ContentStatus` are new enums, because those are closed sets fixed by the requirements. The importer rejects an item referencing a topic that is not declared in the taxonomy file, which is what keeps a documented and versioned taxonomy (NFR-MAINT-001) honest rather than aspirational.
10. **Curated items have no detail page; original lessons do.** A curated item renders as a card in the path/course listing with title, publisher attribution, tags, duration, last-reviewed date, and an anchor straight to the external URL with `target="_blank" rel="noopener noreferrer"`. Only `SourceType.ORIGINAL` items get `/lessons/[slug]`. Rationale: NFR-COMP-001 wants us linking to the source, and an interstitial page inserts a click between the learner and the resource while adding a route that has nothing platform-authored to show. Consequence to be honest about: when FR-PROG and FR-RATE land, their per-item controls for curated items must live on the card, not on a detail page — a deliberate, recorded constraint, not an oversight.
11. **Content routes render dynamically at request time at R1 (`export const dynamic = "force-dynamic"`), with per-request deduplication via React `cache()`.** Content is exactly the slow-changing data NFR-SCALE-004 wants cached, and ISR (`revalidate`) is the obvious fit — but every content route reads Prisma, and the CI `build-and-test` job builds against a placeholder `DATABASE_URL` with no database behind it, so prerendering these routes at build time would break the build. Dynamic rendering keeps CI honest and is comfortably inside the NFR-PERF-001 two-second FCP budget for a small library served from a co-located Neon instance. Promoting them to ISR (or `use cache` with tag-based invalidation triggered by the importer) is a documented follow-up tied to NFR-SCALE-004, deliberately left to the item that also decides search caching. Rejected: giving the CI build job a live Postgres service purely so it can prerender — doubles build-job runtime for a caching win the R1 library size does not need.
12. **The importer runs as a `tsx` script (`npm run content:import`), not as a Prisma `seed` hook or an API route.** It is an operational tool a human runs deliberately, dry-run first; wiring it to `prisma db seed` would conflate schema seeding with content operations, and exposing it as an authenticated API route would be a mini admin UI, which R1 explicitly does not want and which NFR-SEC-006 (RBAC, R2) does not yet exist to protect. Playwright's global setup calls the same importer function directly so local and CI e2e runs are self-seeding.
13. **Seeded lesson prose is visibly labelled as sample content, via one build-time constant rather than a schema column.** Confirmed with the human (Risks #2): the original lessons in the R1 pack are placeholder editorial written to demonstrate the mechanisms, not reviewed instructional material, so every one of them carries a small, unmissable “Sample content — not yet reviewed” notice (`<SampleContentBadge>`) on its lesson page and on its card in path and course listings. The signal is `sourceType === ORIGINAL` **plus** the pack-level `SAMPLE_CONTENT_LIBRARY` constant in `src/lib/content/taxonomy.ts`, because at R1 *every* original item in the pack is seed prose — there is no reviewed original content for a per-item flag to distinguish it from, so one constant expresses exactly as much truth as a column would and is removed in a single edit once the library is editorially reviewed. Curated items are **not** labelled: they are real third-party resources and already carry publisher attribution and a last-reviewed date. Rejected: **an `isSample`/`reviewState` column on `ContentItem`** — it needs a migration, a frontmatter field, and an import rule, and its value would be identical on every row this item ships; the durable “has a human reviewed this” axis already exists as `lastReviewedAt`/`reviewCadenceDays`/`nextReviewDueAt` (decision #7), and a second parallel review flag would compete with it. Rejected: writing the disclaimer into the lesson body prose — unmissable only if every author remembers it, inconsistent in placement, and impossible to remove later in one edit.

## Prisma schema design

Added to the existing `prisma/schema.prisma` alongside the auth models. The `RoleArchetype` and `ProficiencyLevel` enums are **reused as-is**; no auth model is modified. New tables are `@@map`ped to snake_case names.

New enums:

- `ContentFormat { ARTICLE, VIDEO, INTERACTIVE, COURSE, PAPER, PODCAST, TOOL }` — the FR-PATH-004 "format" axis, a closed set, documented in `docs/content/taxonomy.md`.
- `SourceType { ORIGINAL, CURATED }` — the FR-PATH-004 "source type" axis. A single enum rather than an overlapping "kind" concept: `ORIGINAL` requires `body`, `CURATED` requires `externalUrl` plus `sourcePublisher`, enforced by the Zod import schema (a discriminated union) rather than a database check constraint.
- `ContentStatus { DRAFT, PUBLISHED, RETIRED }` — applies to `RoleProfile`, `Path`, `Course`, `ContentItem`, `GlossaryTerm`. Only `PUBLISHED` renders publicly.

New models:

- **`RoleProfile`** — the FR-SEARCH-004 landing-page copy for one archetype. `id`, `role RoleArchetype @unique`, `slug String @unique` (URL segment, e.g. `technical-builder`), `title`, `summary`, `body` (Markdown: who this is for, what you will learn), `status`, timestamps.
- **`Path`** — `id`, `slug @unique`, `roleArchetype`, `level`, `title`, `summary`, `description` (Markdown), `status`, timestamps, `courses PathCourse[]`. `@@unique([roleArchetype, level])` (Decisions #5), `@@index([status])`.
- **`Course`** — `id`, `slug @unique`, `title`, `summary`, `description` (Markdown, optional), `status`, timestamps, `paths PathCourse[]`, `items CourseItem[]`. No duration column: estimated duration is summed from its items at read time so it cannot drift.
- **`PathCourse`** — `id`, `pathId`, `courseId`, `position Int`, both relations `onDelete: Cascade`. `@@unique([pathId, courseId])`, `@@index([pathId, position])`. Deliberately **no** unique constraint on `position` — the importer rewrites a path's ordering wholesale inside one transaction, and a unique position constraint would trip on transient intermediate states.
- **`CourseItem`** — same shape for `courseId`/`contentItemId`/`position`; `@@unique([courseId, contentItemId])`, `@@index([courseId, position])`.
- **`ContentItem`** — the atomic unit and the stable id everything later hangs off. `id String @id @default(cuid())`, `slug @unique` (author-controlled, stable), `title`, `summary`; tagging (FR-PATH-004): `roles RoleArchetype[]`, `level ProficiencyLevel`, `format ContentFormat`, `estimatedMinutes Int`, `sourceType SourceType`, `topics Topic[]` (implicit m2m); original-lesson fields: `body String?` (Markdown), `videoUrl String?`, `videoCaptionsUrl String?`, `videoPosterUrl String?`, `videoDurationSeconds Int?`; curated fields: `externalUrl String?`, `sourcePublisher String?`, `sourceAuthor String?`, `sourcePublishedOn DateTime?`, `attributionNote String?`; lifecycle (FR-PATH-007): `status`, `publishedAt DateTime?`, `retiredAt DateTime?`, `lastReviewedAt DateTime`, `reviewCadenceDays Int`, `nextReviewDueAt DateTime`, `version Int @default(1)`, `contentHash String`, timestamps. Indexes: `@@index([status])`, `@@index([sourceType])`, `@@index([level])`, `@@index([nextReviewDueAt])`. No GIN index on `roles` and no tsvector column — filtering and search are the FR-SEARCH item's decision, and a sequential scan over the year-one 5,000-item target (NFR-SCALE-002) is not a performance problem in the meantime.
- **`ContentItemVersion`** — `id`, `contentItemId` (`onDelete: Cascade`), `version Int`, `contentHash`, `snapshot Json`, `changeNote String?`, `lastReviewedAt`, `createdAt`. `@@unique([contentItemId, version])`, `@@index([contentItemId])`. Append-only (Decisions #8).
- **`Topic`** — `id`, `slug @unique`, `label`, `description String?`, `items ContentItem[]`. Declared in `content/taxonomy.yaml` (Decisions #9).
- **`GlossaryTerm`** — `id`, `slug @unique`, `term`, `shortDefinition String` (plain text, capped at 200 characters by the Zod schema; used for the inline contextual definition), `body String` (Markdown long definition for the term page), `aliases String[]`, `relatedSlugs String[]`, `lastReviewedAt`, `status`, timestamps. `@@index([term])`.

Explicitly **not** added: any `Progress`, `Rating`, `Bookmark`, `Certificate`, or search-index model; any user-referencing column on a content table; any admin/RBAC column; and no `isSample`/`reviewState` column — the sample-content notice is a build-time constant plus `sourceType`, not per-row data (decision #13).

Migration: one migration (`npx prisma migrate dev --name add_content_model`), additive only — it touches no existing auth table and drops nothing.

## New manual provisioning steps (human-only)

- [ ] After each deploy that changes `content/`, run `npm run content:check` and then `npm run content:import` against the production (Neon) `DATABASE_URL`. **Fails visibly**: without it the deployed site renders empty paths — the pages work, they just have nothing in them. This is the R1 content-ops process, and it goes away when FR-ADMIN-002's admin UI lands at R2.
- [ ] Record and upload the one designated lesson video plus its WebVTT captions file to Vercel Blob, then **uncomment** that lesson's `video` block, paste in the resulting CDN URLs, and re-run `npm run content:check` followed by `npm run content:import`. **Degrades gracefully by design**: until then the pack holds no video URL at all, so the lesson renders as text with no video element and nothing looks broken to a visitor; the FR-PATH-005 markup is proven by the `lesson-video` unit test (task 41) and the captions-required schema test, so nothing goes red either — but the video half of FR-PATH-005 is not demonstrable on the live site until this is done.
- [ ] Manually open every curated link in the seed pack once before ship and confirm it resolves and that the recorded publisher/author attribution is accurate (NFR-COMP-001). Automated link checking is NFR-AVAIL-004, R2.
- [ ] Set a recurring calendar reminder for the content review cadence (curated 90 days, original 365 days) per `docs/content/authoring-guide.md`. Nothing in the app enforces it at R1; FR-ADMIN-004's automated flagging is R2.
- [ ] No new environment variables, accounts, or services are introduced by this item — the existing Neon and Vercel Blob provisioning covers it.

## Acceptance criteria

1. A path exists in the database for each of the six R1 role x level combinations, each holding an ordered sequence of courses which hold an ordered sequence of content items; `/paths/technical-builder/zero-knowledge` renders that exact order. _(FR-PATH-001, FR-PATH-002)_
2. Every content item stores and displays all six required tags — role(s), level, topic(s), format, estimated duration, and source type — and the importer refuses a file missing any of them or referencing an undeclared topic. _(FR-PATH-004, NFR-MAINT-001)_
3. An original lesson at `/lessons/<slug>` renders its stored Markdown body as real HTML elements (headings, lists, code, links), with no `dangerouslySetInnerHTML` anywhere in the codebase and with raw HTML in a body rendered as literal text; and, while `SAMPLE_CONTENT_LIBRARY` is on, that lesson page and every original item's card in a path or course listing carry a visible “Sample content — not yet reviewed” notice, curated items carry none, and turning that one constant off removes all of them. _(FR-PATH-005, NFR-SEC-007, decision #13)_
4. The FR-PATH-005 video path is proven without ever shipping a broken player: `<LessonVideo>` renders a native `<video controls preload="metadata">` with a `<track kind="captions" default>` pointing at an absolute CDN URL when the item has a video, and renders nothing at all when it does not; the import schema rejects a `video` block declared without `captionsUrl`; and the seed pack contains no video URL, live or placeholder (the designated lesson's block ships commented out pending the manual upload step), so no seeded page renders an empty or failing video element. Verified by component and schema unit tests rather than by e2e against seeded data. _(FR-PATH-005, NFR-SCALE-003)_
5. A curated item renders as an anchor to its external URL with `target="_blank"` and `rel="noopener noreferrer"`, shows its publisher (and author where recorded) as visible attribution, and no external content is copied into the database or the repo. _(FR-PATH-006, NFR-COMP-001)_
6. Every content item stores `lastReviewedAt`, `reviewCadenceDays` (90 curated / 365 original by default), `nextReviewDueAt`, and a `version`; changing a file and re-importing bumps `version` and appends a `ContentItemVersion` snapshot; re-importing an unchanged pack changes nothing and reports every item as unchanged. _(FR-PATH-007)_
7. A `glossary:` link in a lesson body renders as an accessible inline definition revealed on both hover and keyboard focus, linking to `/glossary/<slug>`; the importer fails with a named error if any `glossary:` link has no matching term. _(FR-PATH-008, NFR-A11Y-004)_
8. A signed-in user can change role and/or level from a path page or the dashboard, is taken to the corresponding path, and the change persists on their profile; at least one content item appears in both the old and the new path, and it is a single row with a single id in both. _(FR-PATH-009, FR-ACC-006)_
9. `npm run content:check` validates the pack without writing and exits non-zero with an aggregated, file-attributed error list on any problem; `npm run content:import` applies it in one transaction and prints created/updated/unchanged/retired counts. Removing an item from the pack and re-importing marks it `RETIRED` and removes it from path rendering — and the row, with its id, still exists. _(FR-ADMIN-001, decision #2)_
10. `/paths/technical-builder` and `/paths/executive-non-technical` are public pages describing the archetype and listing all three levels with their paths. _(FR-SEARCH-004)_
11. Every route added by this item — `/paths`, `/paths/[role]`, `/paths/[role]/[level]`, `/courses/[slug]`, `/lessons/[slug]`, `/glossary`, `/glossary/[slug]` — is fully readable with no session, and unknown or retired slugs return a 404 rather than an error page. _(FR-ACC-008)_
12. `prisma/schema.prisma` contains no `Progress`, `Rating`, `Bookmark`, or `Certificate` model and no user-referencing column on any content table; the new migration applies cleanly to a database already holding the auth tables and alters none of them. _(scope discipline)_
13. `docs/architecture/content.md` states, as a commitment the next work items inherit, that progress keys on `(userId, contentItemId)` and ratings on `courseId`/`pathId`, referencing the ids created here. _(decision #6, FR-PATH-009 retention half)_
14. The new pages are usable at 375px, 768px, and 1280px, every interactive element is keyboard-operable with a visible focus ring, and the glossary inline definition is reachable by keyboard alone. _(NFR-A11Y-002, NFR-A11Y-004)_
15. `docs/content/taxonomy.md` documents every role, level, topic, format, and source-type value and matches `content/taxonomy.yaml`; `docs/content/authoring-guide.md` is sufficient for someone who has never seen the repo to add a curated item and an original lesson and get them live. _(NFR-MAINT-001, NFR-MAINT-005)_
16. `npm run lint`, `npm run format:check`, `npm run test`, `npm run build`, and `npm run test:e2e` all pass locally, and both CI jobs stay green — including `build-and-test`, which builds with a placeholder `DATABASE_URL` and must not attempt to prerender any content route. _(NFR-MAINT-004, decision #11)_

Lower-stakes notes (no answer needed):

6. This item creates obligations for later work items, recorded so they are not surprises: FR-PROG must key progress on `(userId, contentItemId)` and must put per-item controls for curated items on the item card, since curated items have no detail page (decision #10); FR-RATE attaches to `Course`/`Path` ids; and FR-ADMIN-002's admin UI, when it lands, must decide whether the file pack becomes read-only bootstrap data or stays the source of truth with the UI writing back to it — a two-writer content system is the failure mode to avoid, and it is out of scope to solve now.
7. `roles` is a Postgres enum array with no GIN index, and there is no full-text search column. Deliberate: the FR-SEARCH item chooses the search technology (requirements section 5 leaves it open) and should own the indexing that goes with it. At the year-one 5,000-item target neither omission is a performance problem.
8. Estimated duration for a course or a path is summed from its items at read time rather than stored, so it cannot drift out of sync. If path pages ever get slow, this is the obvious thing to denormalize.
9. `Path` carries `@@unique([roleArchetype, level])`. If a future item ever wants A/B variants of the same role x level path, that constraint has to go. FR-PATH-010's custom paths do not need it removed (they are a separate user-owned model), but it is the one constraint in this schema a plausible future feature could collide with.
10. The `NOT_SURE_YET` role archetype has no path and no `RoleProfile` — the dashboard and switcher route those users to `/paths` to browse. That is the right behaviour, but it means a user can finish onboarding and have no path, which the FR-PROG dashboard work will also need to handle.
11. `ContentItemVersion.snapshot` is untyped `Json`. That is deliberate (a snapshot must survive future schema changes without a backfill), but nothing type-checks a historical snapshot's shape. If a later item renders old versions in a UI, it should validate them through a versioned Zod schema at read time rather than trusting the column.
12. The seed pack deliberately includes at least two shared items so that overlap is exercised by a test rather than merely asserted in prose. If the real content library ends up with no overlap between paths, FR-PATH-009's retention clause becomes vacuously true — worth watching as the library grows.
